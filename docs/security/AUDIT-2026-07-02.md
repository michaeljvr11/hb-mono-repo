# Security Audit — HB Monorepo (hb-ecommerce.com)

**Date:** 2026-07-02
**Scope:** Full repo — `apps/api` (NestJS) + `apps/web` (Angular) + `libs/shared`.
**Method:** Static review of auth, authorization, DB/schema, and general web-security
surface, cross-checked against the settled decisions recorded in `hb-vault`
(`Auth & Roles`, `HB Domain Model`). Ran `npm audit`.

This is an honest picture: a lot of the auth core is genuinely well-built. The
findings below are ranked by severity, and the **Already Solid** section is not
padding — it records the patterns worth *keeping* so future work builds on them.

## CRITICAL

### C1 — Self-registration allows arbitrary role assignment (privilege escalation)

**Where:** `apps/api/src/auth/dto/register.dto.ts:21-23`,
`apps/api/src/auth/auth.service.ts:43-55`, `libs/shared/src/contracts/auth.ts:15`.

`RegisterDto` exposes an optional, *validated* `role` field:

```ts
@IsEnum(UserRole)
@IsOptional()
role?: UserRole; // defaults to CUSTOMER; admins create vendors
```

Because the field carries validators, the global `ValidationPipe({ whitelist: true })`
**keeps** it. `AuthService.register` then spreads it straight into user creation:

```ts
const { email, password, rememberMe, ...rest } = registerDto; // rest = { firstName, lastName, role }
const user = await this.usersService.create({ email, password, ...rest });
```

`POST /api/auth/register` is `@Public()`. So an unauthenticated attacker can send:

```json
{ "email": "attacker@evil.com", "password": "hunter2xyz", "role": "admin" }
```

…and receive a fully-privileged **admin** account plus a valid session, in one call.
This is the single most serious issue in the codebase: complete vertical privilege
escalation from anonymous to admin. The frontend only ever sends `role: 'customer'`,
but the frontend is not a trust boundary — the API accepts whatever is posted.

The `role` field on register was never needed for a legitimate flow: admins create
vendor accounts via `POST /vendors/admin` and change roles via
`PATCH /admin/users/:id/role`. Vendor self-onboarding sets the role server-side in
`VendorsService.create`. So the correct fix is to remove `role` from the public
registration contract entirely.

**Fix (this PR):** drop `role` from `RegisterRequest` (shared), from `RegisterDto`,
and from the web register component; force `UserRole.CUSTOMER` in `AuthService.register`
as defense-in-depth. Regression test added.

## HIGH

### H1 — No rate limiting on authentication endpoints

**Where:** `apps/api/src/main.ts`, `apps/api/src/app.module.ts` (no `@nestjs/throttler`).

There is no throttling anywhere. `POST /auth/login`, `/auth/forgot-password`,
`/auth/reset-password`, `/auth/verify-email`, `/auth/register` and `/auth/refresh`
all accept unlimited attempts. Consequences:

- **Credential stuffing / brute force** against `/auth/login`.
- **Password-reset & verification email bombing** (each `forgot-password` call to a
  real address triggers a Resend send — abuse cost + spam-listing risk).
- **Reset-token brute force**: tokens are strong (256-bit), so this is theoretical,
  but rate limiting is the standard backstop.

**Fix (this PR):** add `@nestjs/throttler` with a sane global default and a tighter
per-route limit on the sensitive auth endpoints via `@Throttle`.

### H2 — Public admin-bootstrap endpoint has a first-mover race

**Where:** `apps/api/src/auth/auth.controller.ts:53-59`,
`apps/api/src/auth/auth.service.ts:128-158`.

`POST /auth/bootstrap-admin` is `@Public()` and creates an admin whenever
`countByRole(ADMIN) === 0`. It is self-sealing *after* the first admin exists, but on
a freshly-migrated production database there is a window in which **whoever calls it
first becomes admin** — including an attacker who knows the deployment is new. The
impact is a full admin takeover, so the small window still matters.

**Fix (this PR):** gate the endpoint on a server-side secret (`ADMIN_BOOTSTRAP_SECRET`).
When the env var is set, the request must present the matching secret; in `production`
the secret is **required** (the endpoint fails closed if it is unset). Local/dev keeps
working with no secret configured, preserving the "runs without config" ethos.

## MEDIUM

### M1 — No security headers (helmet not installed)

**Where:** `apps/api/src/main.ts`.

No `helmet` (or equivalent). Responses ship without HSTS, `X-Content-Type-Options`,
`X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, or a Content-Security-Policy.
For an e-commerce app this is table stakes — HSTS in particular hardens the HTTPS
posture, and a CSP is the main structural mitigation for XSS (and thus for M4, the
localStorage token). HTTPS itself is expected to be terminated at the proxy/load
balancer in production; helmet's HSTS makes that enforcement sticky in the browser.

**Fix (this PR):** add `helmet()` in `bootstrap()`, with HSTS enabled and a
conservative CSP.

### M2 — Google OAuth: missing `state` and unverified-email linking

**Where:** `apps/api/src/auth/strategies/google.strategy.ts`,
`apps/api/src/auth/auth.service.ts:98-123`.

Two defense-in-depth gaps in an otherwise clean server-side Authorization-Code flow:

1. **No `state` parameter.** `passport-google-oauth20` is configured without
   `state: true`, so the callback isn't bound to the initiating request → classic
   OAuth **login-CSRF / authorization-code injection** exposure.
2. **`email_verified` not checked.** `validateOAuthLogin` links an incoming Google
   profile to an existing local account purely by email address
   (`profile.emails?.[0]?.value`) without checking the profile's verified flag. Google
   normally only returns verified emails for this provider, but best practice is to
   check it — otherwise an unverified-email edge case could link into an existing
   account.

**Fix (this PR):** enable `state`, and reject the login unless the Google email is
marked verified.

### M3 — `multer` ≤ 2.1.1 (two High-severity DoS advisories)

**Where:** `apps/api/package.json:38` (`"multer": "^2.1.1"`).

`npm audit` reports two High advisories against multer ≤2.1.1 (GHSA-72gw-mp4g-v24j,
GHSA-3p4h-7m6x-2hcm — DoS via deeply-nested field names / incomplete cleanup of
aborted uploads). The only multipart route is `POST /products` (vendor/admin-gated),
so exposure is limited to authenticated sellers, but it's a clean fix: **multer 2.2.0**
is published and outside the vulnerable range.

**Note:** `npm audit fix --force` wants to *downgrade* `@nestjs/core` to 7.5.5 — that
is the audit tool misreading the monorepo tree. Do **not** run it. The real fix is the
targeted `multer` bump, which is non-breaking.

**Fix (this PR):** pin `multer` to `^2.2.0`.

### M4 — Access token stored in `localStorage`

**Where:** `apps/web/src/app/core/auth/auth.service.ts:26,126,148`.

The vault's settled design (`Auth & Roles`) says **"Access Token — short lived —
stored in memory."** The implementation instead persists it in `localStorage`. That
makes the token readable by any successful XSS, which is the higher-impact half of a
token-theft chain. The refresh token is correctly httpOnly, so this only exposes the
15-minute access token — but it's still a deviation from the agreed design.

A true fix (in-memory access token + silent refresh-on-load) is a frontend refactor
that changes page-reload UX, so it is **not** bundled into this security PR. Instead
this PR adds a CSP (M1) to reduce the XSS surface that makes the token stealable, and
flags the in-memory migration as a tracked follow-up. Documented in the vault.

## LOW

- **L1 — `ProductUpdateDto.vendorId` is accepted but ignored.**
  `apps/api/src/products/dto/product-update.dto.ts:42-43`. `ProductsService.update`
  never copies `vendorId` onto the entity, so it is inert today — but the field invites
  a future "just `Object.assign` the DTO" refactor that would silently enable
  cross-vendor product reassignment. Removed from the DTO. *(Fixed.)*

- **L2 — `seed.ts` hardcodes a weak admin credential.**
  `apps/api/src/database/seed.ts:28-38` creates `admin@hb.local / Admin1234!` and prints
  it. Fine for local dev (idempotency-guarded), dangerous if ever run against a real DB.
  Guarded to refuse to run in `production`. *(Fixed.)*

- **L3 — `JWT_EXPIRATION` read with no fallback.**
  `apps/api/src/auth/auth.service.ts:218`. If the env var is missing in production,
  `expiresIn` is `undefined` and the signed access token **never expires**. Added a
  safe `'15m'` default. *(Fixed.)*

- **L4 — `VendorsController.update` role vs. ownership mismatch.**
  `apps/api/src/vendors/vendors.controller.ts:75-79` allows `ADMIN`, but
  `VendorsService.update` enforces owner-only and would 403 an admin. Not a vulnerability
  (it fails *closed*), but a correctness inconsistency. Aligned the service to let admins
  through. *(Fixed.)*

- **L5 — Single refresh-token slot per user.** `users.currentRefreshToken` holds exactly
  one hash, so logging in on device B invalidates device A's ability to refresh. This is
  a UX/design property, not a vulnerability. *Documented, not changed* — multi-session
  support (a sessions table) is a product decision, not a security fix.

- **L6 — CORS.** `apps/api/src/main.ts:8-33`. The config is safe: a fixed allowlist with
  `credentials: true`, no origin reflection, explicit methods/headers. The default list's
  `https://hnb.co.za` matches the prod frontend (`apps/web/src/environments/environment.ts`
  → `api.hnb.co.za`), so web+API share the `hnb.co.za` registrable domain and the
  `SameSite=strict` refresh cookie works. **Action:** confirm `CORS_ORIGINS` is set
  explicitly per-environment in prod. *Documented.*

## ALREADY SOLID (keep these patterns)

- **Password hashing** — `bcryptjs` at cost **12**, both on insert
  (`User.@BeforeInsert`, `user.entity.ts:72-75`) and on reset
  (`auth.service.ts:178`). Appropriate for 2026.
- **Password reset flow** — 256-bit random token, **SHA-256 hashed at rest**
  (`auth.service.ts:251`), 1-hour expiry, single-use (cleared on use), refresh session
  dropped on reset (`users.service.ts:75-85`), and **no user enumeration** (identical
  response whether or not the email exists, `auth.service.ts:160-170`). Textbook.
- **Refresh tokens** — rotating, **bcrypt-hashed at rest**, delivered only in an
  httpOnly cookie, env-driven `SameSite` defaulting to `strict`, remember-me TTL encoded
  in the JWT so it survives rotation. The topology reasoning is well-documented.
- **Authorization architecture** — global `JwtAuthGuard` + `RolesGuard` as `APP_GUARD`
  (`app.module.ts:46-50`); secure-by-default (everything authed unless `@Public`),
  role-gated with `@Roles`. Applied **consistently** across every controller reviewed.
- **Horizontal-escalation defense** — ownership checks live in the service layer
  (`ProductsService.ensureCanManageProduct`, `VendorsService.update`), exactly as the
  vault mandates. Users can't reach each other's data.
- **Admin self-protection + auditing** — admins can't change their own role or
  deactivate themselves (`admin.service.ts:62-63,83-84`); every privileged mutation
  writes to an append-only audit log.
- **SQL injection** — none. All data access is via TypeORM repositories, parameterized
  query builders, and `ILike` operators (`admin.service.ts:39`,
  `vendors.service.ts:204-217`). No string-concatenated SQL.
- **Input validation** — global `ValidationPipe` with `whitelist + transform`; every
  input is a DTO implementing a `@hb/shared` contract with class-validator decorators.
- **XSS** — no `bypassSecurityTrust*`, no `[innerHTML]`, no `dangerouslySetInnerHTML`
  anywhere in `apps/web`. Angular's default contextual escaping is intact.
- **Secrets** — no `.env` is tracked (only `.env.example`); frontend env files hold no
  secrets; `MailService` no-ops (with a warning) when `RESEND_API_KEY` is absent; no
  tokens or PII are logged.
- **File uploads** — MIME + size validation at two layers (Multer `fileFilter` +
  `ParseFilePipeBuilder`), and stored filenames are freshly-generated UUIDs, so a
  malicious `originalname` can't drive path traversal.
- **Data-scoping on public reads** — public product/vendor lookups filter to
  `APPROVED`/published only; pending/rejected/suspended records 404 rather than leak.

## Database design assessment (single DB, three user types)

The prompt asked specifically whether storing customers, admins, and vendors in one
database is safe as-is. **Conclusion: keep it. No restructuring needed.**

- All three types are one `users` table discriminated by a `role` enum column
  (`user.entity.ts:23-29`, migration `1781136000000`). This is the conventional,
  well-understood pattern; it keeps foreign keys (orders, addresses, carts, vendor
  profiles) simple and lets one auth stack serve everyone. The vault treats this as a
  settled decision, and nothing in the review argues against it.
- The genuine risk was never *co-location* — it was **who can write the `role`
  column**. That risk was real and is exactly finding **C1** (mass assignment on
  register). With C1 fixed, role transitions happen only through the admin-only,
  audited `PATCH /admin/users/:id/role` path.
- Splitting admins into a separate table/database would add join/operational complexity
  without removing the mass-assignment class of bug — you'd still need the same
  server-side write discipline. The higher-leverage controls are the ones this PR adds:
  no client-settable role, centralized guards, and audit logging on role changes.

If the platform later needs true **multi-session** or per-type credential policies, a
dedicated `sessions` table (see L5) is the natural next step — but that's a product
decision, not a security prerequisite.
